## Initial scaffold

  structure, SQLAlchemy models, the vision/embedding services, the
  mismatch guard, batch job, and seed/eval scripts.
- The initial scaffold used placeholder images (generated colored

## Vision pipeline

- The scaffold's vision model name (`gemini-1.5-flash`) was already
  retired by Google by the time I ran it — it returned a 404. Had to
  work through two more model-name updates before landing on a model
  that actually worked with my API key (`gemini-3.8-flash`). This is a
  real lesson in not trusting a hardcoded model name to stay valid —
  Google's free-tier models get deprecated on their own schedule.
- The free tier hit a hard **5 requests/minute** rate limit partway
  through the first batch run (11/40 images succeeded before failing).
  Fixed by adding `time.sleep(13)` between each vision call in
  `app/batch_jobs.py`'s processing loop, to stay under that limit.
- After the rate-limit fix, the batch job hit a **separate, harder
  limit: 20 requests/day** on this account's free tier. With 29 images
  still untagged, I used the fallback approach FlyRank's own Q&A thread
  explicitly approved: instead of calling the live API, I had the tags
  for the remaining images generated by viewing each real photo directly
  and writing the tag JSON by hand (via Claude, acting as the vision
  step manually) into `data/mock_vision/`, then ran the batch job with
  `USE_MOCK_VISION=true` so it read those files instead of calling the
  API. The validation and storage code is identical either way — only
  the source of the JSON changes. **11 of 40 images were tagged by the
  live Gemini API; the remaining 29 were tagged this way.**

## Matching & guard tuning

- `SIMILARITY_THRESHOLD` needed two different values depending on the
  embedding backend. The scaffold's default (0.55) assumed real semantic
  embeddings; with the local hash-based fallback (used before I had a
  working API key), actual scores for a genuinely matching post/image
  pair only reached ~0.17, so the threshold had to be lowered to ~0.12
  for the fallback to accept anything at all. Once I switched to real
  Gemini embeddings, this needed re-checking again — real embeddings
  produce a different score distribution entirely.
- Probe 1 (low-confidence flagging): the two low-confidence examples (fox_08 = 0.46, wolf_08 = 0.50) are
  hand-assigned values in AI-written mock JSON, set to exercise the flagging path; they are not model-measured.
  To check, I re-tagged both with live Gemini (gemini-3.8-flash) on 2026-10-10 and it returned 0.98 for each, so
  the guard and its tests are real but these two confidence values are synthetic. I kept the hand-assigned values
  and disclose them here and in the README. Tag provenance: 11 images (the 8 bears, deer_01, deer_02, deer_04) were
  tagged by live Gemini; the other 29 were written by AI (Claude) viewing each photo.

## Things AI got wrong / I had to fix — the real debugging story

This is the part of the brief that matters most, so I'm being specific
about three separate, real bugs found and fixed during development, not
hypothetical ones:

**Bug 1 — substring matching let "red" match inside "bred".**
The guard's category-conflict check originally used `"word" in post_text`
to check whether a subject's words appeared in the post. Python's `in`
does substring matching, not word matching — so checking whether "red"
(from the subject "red fox") appeared in a post about dogs returned
`True`, because "red" is literally a substring of "bred" ("...have
been **bred** alongside humans..."). This silently satisfied the "subject
is mentioned in the post" check and let the guard skip its conflict
check entirely, so a fox image got suggested for a dog post with no
warning. Fixed by switching to `\b[a-z]+\b` regex word-boundary
tokenization, so only whole words count as matches.

**Bug 2 — exact word matching failed on plurals.**
After fixing Bug 1, a very similar failure showed up for a different
reason: the subject "domestic dog" contains the word "dog" (singular),
but the post text says "dog**s**" (plural) — and `"dog" == "dogs"` is
false as exact strings, even with word-boundary matching. So the guard
still failed to recognize that a dog-labeled image and a post about dogs
were actually the same subject. Fixed by adding a small singularization
function (`_normalize_word`) that strips common plural suffixes (with a
short irregular-plurals list for cases like wolf/wolves) before
comparing words on both sides.

**Bug 3 — a stopword inside a subject label defeated the whole check.**
Even after Bugs 1 and 2 were fixed, one specific image (`bear_03.jpg`)
still slipped through incorrectly for a dog-themed post. Its vision
subject had been saved as `"polar bear and cub"` instead of a clean
species name — and the connector word **"and"** in that label matched
the word "and" in the post text (which, like almost any English
sentence, contained "and" somewhere). That single generic word match was
enough to satisfy "the image's subject is referenced in the post" and
bypass the conflict check for every post, regardless of actual topic.
Fixed by filtering out common stopwords (and, the, with, of, for, etc.)
before extracting a subject's meaningful words.

All three bugs were found the same way: running `scripts/eval.py`,
seeing a wrong result, then writing a small standalone script to call
`_category_conflict()` directly with the exact failing inputs to see
what it actually returned versus what I expected — rather than guessing
at the fix from the symptom alone.

**A fourth issue, not a code bug:** the Gemini embedding API call failed
with `Invalid model name: 'gemini-embedding-001'` even though the model
name itself was correct — this SDK version requires a `models/` prefix
on every model name passed to `embed_content()`. Fixed by changing
`model="gemini-embedding-001"` to `model="models/gemini-embedding-001"`
in `app/embedding_service.py`.

My first write-up called the 10% a "corpus artifact, not a defect". **That explanation was wrong, and a review

## Review & fix session (AI-assisted: Claude reviewed the repo and made these changes)

I asked Claude to review the whole project against the brief. What it found, and what changed — I verified the image
findings myself by opening `reports/tag_review.html`.

**Found (the real reasons for 1/10):**
1. **Tags did not match the photos for 10 of 40 images** (6 wolves, 4 dogs). Files had been renamed/reshuffled after tagging,
   so e.g. `wolf_01.jpg` was actually a husky, `wolf_03.jpg` was a howling pack (its stored caption described a different file),
   `dog_05.jpg` was a border collie (stored: a beach dog). Embeddings were built from those wrong captions.
   *Fix:* re-wrote tags for those 10 from the actual photos, renamed the husky to `dog_09.jpg` (kept deliberately as a
   wolf look-alike hard negative), and added `scripts/review_sheet.py` so tag/photo alignment can be eyeballed in 2 minutes.
   Tags for those 10 are hand-written (not live Gemini) — to replace them with live output:
   `USE_MOCK_VISION=false python scripts/run_batch.py --reprocess wolf_03.jpg wolf_04.jpg wolf_05.jpg wolf_06.jpg wolf_07.jpg dog_05.jpg dog_06.jpg dog_07.jpg dog_08.jpg dog_09.jpg`.
2. **The eval set was ill-posed.** Posts like "Red Fox Breeding Season Explained" don't describe any particular photo, so labeling
   `fox_02.jpg` "correct" among 8 fox photos was arbitrary; some labels were the wrong species ("Brown Bear Hibernation" →
   a *black* bear; "White-Tailed Deer" → an unrelated deer). *Fix:* rebuilt the eval into four tiers (specific / concept / no-match /
   hard no-match), labels assigned by looking at the photos *before* running the matcher.
3. **Probe 4 was failing:** `SIMILARITY_THRESHOLD` was still 0.12 (fallback-embedding scale). With real Gemini embeddings the
   "Best Programming Languages" post was accepted with a wolf photo (similarity 0.72). Measured on my stored vectors: unrelated posts
   0.717/0.730 best-image similarity vs 0.777+ for correct posts → 0.75. Added `scripts/tune_threshold.py`.
4. **Guard bug #4:** a generic word shared between subjects ("red" in "red fox" / "red deer") counted as "post mentions this subject",
   so a fox photo could pass for a red-deer post. Also polar-bear photos passed for "brown bear" posts via the shared word "bear".
   *Fix:* compare how strongly the post references the candidate's subject vs every other known subject.
5. **Silent embedding fallback:** if the Gemini call failed, the code silently stored a 128-dim hash vector next to 3072-dim
   Gemini vectors, and cosine returned 0.0 on a length mismatch — scores became meaningless with no error. *Fix:* failures raise,
   the backend is explicit (`EMBEDDING_BACKEND`), dimension mismatch is a loud 409.

**Also changed to meet the brief's requirements:** batch job is now a real background job (was a blocking request with
`sleep(13)` even in mock mode) with a job table, progress, resumable stages and failure alerts; per-*call* cost rows incl. failures;
a daily budget guard; `GET /posts/{id}/images` returns the ranked, explained candidates; new `/posts/{id}/check/{image_id}`
to force a candidate (Probe 3); suggestions are idempotent (previously every GET inserted a duplicate); Alembic migrations;
`capstone.yaml` no longer runs `seed_data.py` (which regenerated placeholder images and would have **overwritten the real photos**);
70 tests (was 11); images resized from 109 MB to 3 MB for the repo.

**Where Claude was wrong / what I should double check:** Claude wrote the eval posts and the replacement tag JSON, so the
labels reflect its reading of the photos — I reviewed `reports/tag_review.html` and the eval labels myself and corrected any I disagreed with.
Claude also could not call Gemini from its sandbox, so every number in the README/EVIDENCE comes from running the scripts on my machine.
